## 2. 第一批：UI 重构

改动集中在 `src/views/home/index.vue` 展示层，不触碰发布逻辑的判断分支。

### 2.1 应用类型折叠面板 + 块头强化

替换 `index.vue:208-569` 的 5 个重复 `table-appconfig` 表格为 `el-collapse`（Element Plus 已在 `main.ts` 全局注册，可直接使用；仓库内属首次引入，无既有先例）：

```
┌ 发布信息 ──────────────────────── [生成发布文件] [修改配置] [刷新] ┐
│ [项目选择 ▼__________________]   Dev | Pro                      │
├───────────────────────────────────────────────────────────────────┤
│ ▸ 基础配置（dll方式 · MsBuild · 备份 · 异步上传）      ← 默认折叠 │
│ ▼ 🟦 WebApiHost   2 台服务器 · 4 个发布路径          ✓ 已发布 14:32 [移除] │
│     ├ 🖥 应用服务器A                                                 │
│     │    [ApiSite] D:/Web/Api      [Bff] D:/Web/Bff                │
│     └ 🖥 应用服务器B                                                 │
│ ▸ 🟩 WebClient    1 台服务器 · 2 个发布路径                        │
│ ▸ 🟧 WpfClient    压缩打包 · 应用服务器 server-01                  │
└───────────────────────────────────────────────────────────────────┘
```

要点：
- 五种类型各配主题色 `el-tag`（类型名文字为主；smom 图标集无应用类型专属图标，可选复用现有通用图标如 `fuwuqi`/`chengxuji`，不新增图标资产），面板头显示 **类型名 + 服务器数/路径数摘要**（WpfClient 显示"压缩打包 + 服务器名"），不展开即可扫一眼看清类型↔服务器对应关系。
- 默认全部折叠，页面高度收敛到半屏内。
- 服务器做小节标题；服务标识用 `el-tag` + 路径同行展示，长路径 ellipsis + tooltip，替代嵌套无边框表格。
- "程序集输出路径 / dll方式 / 发布日志选项 / MsBuild / 备份" 收进"基础配置"折叠区，默认折叠为一行摘要。
- 模板重构为 `computed appSections` 数组 + 单个 `v-for`（WpfClient 用 `kind` 字段走特殊分支），消除约 300 行重复模板。

### 2.2 已发布 / 未发布状态徽标（替代置空 clientPath）

面板头右侧状态徽标：`待发布`（灰）→ `发布中`（loading）→ `已发布`（绿 ✓ + 时间）/ `发布失败`（红 ✗）/ `已移除`（灰禁用态）。

实现：
- 页面级 `publishStatus: Record<应用类型, status>`；发布流程中 5 处 `xxx.clientPath = ""`（`index.vue:1032/1040/1062/1070/1078`）改为置 `published` 状态，**不再篡改配置对象**；
- 各 `publishXxx` 返回 `false` 时对应类型置 `failed`；
- **状态重置的单一收口点 = `getPublishAppconfigs()`**——所有配置重载路径（`getProjectDefault` / 刷新按钮 / 切项目 / 切环境 / 对话框 `@refresh`）最终都经过它，在此统一重置为 `待发布`——**不是**发布开始时。原代码的 `clientPath` 清空在发布失败后跨运行保留，形成"失败重试只补发未完成类型"的续发语义，重置时机必须与之对齐；
- 为保持续发语义等价，以下跳过判断需从"`clientPath` 为空"扩展为"`clientPath` 为空**或**状态为 `published`"：
  - `publishWebApiHost / publishWebClient / publishSpcMonitor / publishScheduleServer / publishWpfClient / newPublishWpfClient` 的 `if (!clientPath) return true` 守卫；
  - `getApplicationAssemblys` 内 5 个 `if (xxx.clientPath)` 分支条件；
  - `getConfigItemHosts` 的 filter（原代码失败后点"编译项目"同样跳过已发布类型，不可遗漏）；
  - `projectPublish` 开头的 `serviceNames` 过滤（`index.vue:1004-1006`）——重试时 `deployRecorder.selectedServices` 的取值需与原行为一致，同样排除已发布类型；
- **`generatePublishDialog` 的显隐同样依赖 `clientPath`**（模板 5 处 `v-if`（44/73/104/133/162 行）、590 行服务过滤、337-381 行排除置空），且 `openDialog` 经 `Object.assign` 直接使用传入对象。为保持其"已发布类型不出现在生成范围"的原行为：`onGeneratePublish`（`index.vue:1101`）改为传入**过滤副本**——浅拷贝 `appconfigData` 与 `configItems`，将 `published` 状态类型的 `clientPath` 置空后再传，对话框自身零改动；
- "移除"仍为临时移除语义（刷新恢复），面板显示"已移除"禁用态而非消失。

### 2.3 环境单选：未配置隐藏 + 无配置引导配置向导

- 切换项目时已逐环境查询（`onProjectChange` 的 env 1~4 循环），抽出 `getAvailableEnvironments(projectId)` 复用并**存储结果**；环境单选组改为 `v-for availableEnvironments` 渲染，未配置的环境不渲染。
- **空态分两种情况处理**（避免文案错配）：
  - **未选择项目**（`getProjectDefault` 查不到默认项目、projectId 为空）：提示"请先选择项目"，隐藏环境单选组，不显示环境引导；
  - **已选项目但一个环境都没配**：隐藏环境单选组，空态升级为配置引导：

```
┌────────────────────────────┐
│      （空态插画）           │
│   该项目尚未配置任何发布环境  │
│  [打开配置向导]  [前往应用配置] │
└────────────────────────────┘
```

  - 主按钮"打开配置向导"：发布页直接挂载 `@/views/appconfig/components/projectWizard/index.vue`（`open()` 无参、自带草稿恢复），弹窗内完成配置，无需离开页面；向导已有 `emit('refresh')`（`projectWizard/index.vue:55,200`，appconfig 页同款用法）。发布页刷新需用**条件处理**：已选项目时走 `onProjectChange(state.publishData.projectId)`（对当前项目重探测环境 + 重载配置），未选项目时才走 `getProjectDefault()`——直接绑 `getProjectDefault` 会把用户当前选择的项目重置回默认项目（`getProjectDefault` 无条件取默认项目 id）；
  - 次按钮"前往应用配置"：路由跳转应用配置页。
- 发布功能入口维持现有 `showEmptyAppConfig` 拦截。

## 3. 第二批：健壮性

> 注：本节行号为方案编写时的参考值，第一批已实施、行号已偏移，实施时一律按符号（函数名/类名）定位。

### 3.1 safeJsonParse

- 新增 `src/utils/safeJsonParse.ts`：`safeJsonParse<T>(raw, fallback): T`，解析失败返回 fallback 并 `console.warn`；`publishSections.ts` 的私有 `safeParseArray` 改为基于它实现（避免两套安全解析并存漂移）；
- 模板侧现状（第一批已实施）：`showGenerateDir / showCompressFile` 已随折叠面板重构删除，其职责由 `buildAppSections` 内的安全解析承担，**无需再处理**；模板调用仅剩 `showDllMode` 一处需替换为安全版本；
- 再覆盖发布流程中 **17 处**裸 `JSON.parse`（第一批实施后逐一核实）：`validateTfsLocalPath`、`newPublishWpfClient`、`publishWpfClient`、`getDllModeDateRange`（日期范围分支）、`newCopyWpfAssemblyFile`（3 处）、`copyWpfAssemblyFile`（3 处）、`copyAssemblyFile`（TFS/Git 两处）、`getPublishLogResolveOptions`（TFS/Git 两处）、`showDllMode`（日期范围/TFS/Git 三处）；字段家族为 `dllModeValue / generateDirJson / compressFileJson`，解析失败走原有失败分支并输出明确日志。注意：`copyAssemblyFile / copyWpfAssemblyFile / newCopyWpfAssemblyFile` 内的 `if (!appConfig.clientPath)` 是参数校验（仅被已守卫的调用方触达），不属于本项范围；`getTfsDllFiles / getGitDllFiles` 自身无裸 parse。

### 3.2 服务启停轮询等待反馈

`switchWinService` 的 Windows 服务轮询段（`sc stop/start` 后 150 次 × 2s 循环，按函数名定位）每 20s（每 10 次迭代）追加一条：`等待服务停止/启动…已等待 N s（最长 300s）`。纯追加日志，不改判断与返回逻辑；`switchDockerService` 无轮询循环、不在范围内。

### 3.3 定时执行期间禁用入口（临时护栏）

`isScheduledRunning` 为 true 时，**所有会写入或重载 `state.publishData` 的 UI 入口统一禁用**——不止功能卡/项目下拉/环境单选，还包括：修改应用配置按钮（保存会触发配置重载换掉运行中任务的 appconfigData）、生成SMOM发布文件按钮（可并发触发取程序集、读写本地程序集目录）、面板头移除按钮（改 clientPath 影响运行中任务后续判断）、基础配置区各开关（改运行中读取的备份/发布日志设置）。实施方式分两步：
1. **替换**现有 14 处 `funModule[...].loading == true` 条件（13 处模板绑定 + `onActivated` 内 1 处脚本判断，已核实）为单个 computed `uiLocked = funModule loading || isScheduledRunning`，一处收口；
2. **补加**原本没有禁用条件的写入口——如"生成SMOM发布文件"按钮（当前仅 `@click` 无任何 disabled）、日志清空/复制按钮（清空会丢掉定时任务正在写入的日志缓冲与失败留档）——同样绑 `uiLocked`。
功能卡另在 `onFunModuleHandle` 开头加 `isScheduledRunning` 早退守卫并置灰提示；顶部显示"⏱ 定时发布执行中，请稍候"；`onActivated` 中的 `getProjectDefault()` 在定时执行期间跳过。第三批调度中心上线后由架构根治取代。

### 3.4 上传现状结论（不改，备忘）

- 前端每次调用 `upload_server_files` 只传 1 个顶层条目（文件或子目录，`index.vue:2177-2181` 循环）；
- 后端（`file_module.rs:1890-1954`）支持一次多路径 + 目录递归上传（自动建远程目录）；子目录条目经 `read_files` 返回后同样会被递归上传，功能正确；
- SSH 连接有连接池（`ssh_pool`）复用会话，非逐文件重建连接，实际开销为调用粒度与 IPC；
- 已知小瑕疵：进度"共 N 个文件"统计的是顶层条目数而非实际文件数；
- 若将来优化：采用"整批一次 + 失败批次降级为逐条重试"，保持单文件重试能力，放第三批之后单独评估。

## 4. 第三批：调度中心 + 发布引擎参数化

### 4.1 目标

- A 项目定时发布与 B 项目手动发布**互不干扰**（不同项目可并行）；
- 定时执行脱离页面组件存活，不再与 UI 状态互相踩踏（根治问题 #9）；
- 顺带完成 #14 的等价重构，收敛重复代码。

### 4.2 架构

```
┌─ App 启动 ─────────────────────────────────────────────┐
│  publishScheduler（全局调度器，pinia store / App.vue 级）│
│   ├─ 每 30s 扫描 pending 任务 → 到点自建 ctx 执行        │
│   └─ 并发策略：不同项目并行；同项目+同环境互斥（显式提示）│
└──────────────┬──────────────────────────────────────────┘
               │ 共用同一发布引擎
   ┌───────────▼───────────┐   ┌─────────────────────────┐
   │ composables/          │   │ views/schedule/         │
   │ usePublishFlow(ctx)   │   │ 新路由 /schedule（见3c） │
   │ 首页手动发布：         │   │ 任务表格/新建/改期/取消/ │
   │ ctx = 页面当前选择     │   │ 每任务独立日志查看       │
   │ 日志 → 右侧面板       │   └─────────────────────────┘
   └───────────────────────┘
```

**ctx 设计**：`{ projectId, projectName, environment, appconfig(快照，configItems 需深拷贝防止跨运行突变), assemblyOutPath, status(独立 PublishStatusMap/publishedAt，即第一批引入的徽标状态随运行各自持有——首页面板徽标只绑定当前项目的手动运行，定时任务的徽标在任务页展示), logger(独立 2000 行缓冲), signal(暂停/停止/恢复), deployRecorder(实例), generatePublishLog(实例) }`。现在散落在组件里的共享可变状态（`state.publishData`、`logPrintInfo`、`generatePublishLog`、模块级 `deployRecorder`、`projectAssemblyOutPath`、`publishStatus/publishedAt`）全部收进 ctx，每次发布运行各持一份。注意：`assemblyOutPath` 必须在**构建 ctx 时解析完毕**——原 `getProjectOutPath` 读取页面级 `projectList` 做兜底，定时链路无此状态，须从 projectDb 按 projectId 查询解析，引擎内部不得再读任何页面状态。

### 4.3 子步划分（每步独立签入、可回退）

**3a 引擎抽取**：把 `projectPublish / oneClickPublishing / buildProjects / getApplicationAssemblys / copyAssemblyFile / copyWpfAssemblyFile / newCopyWpfAssemblyFile / publishWebApiHost / publishWebClient / publishSpcMonitor / publishScheduleServer / publishWpfClient / newPublishWpfClient / publishBeforeBackup / serverPublish / switchWinService / switchDockerService` 等函数**机械搬运**到 `usePublishFlow.ts`，仅把"读组件状态"改为"读 ctx"。清单外须一并搬运其依赖闭包（否则半截搬运无法编译）：`getProjectOutPath`（改读 ctx）、`getDllModeDateRange`、`getDllModePatterns`、`getConfigItemHosts`、`validateTfsLocalPath`、`checkCanContinueHome`（改读 ctx.signal）、`getTfsDllFiles / getGitDllFiles`（TFS/Git 命令构造与发布日志生成）、`getPublishLogResolveOptions`、`getServerDetail / getTfsDetail / getGitDetail`、`readDirFiles / createDir / isWinServiceStop`、`initLogs / collectFailLogs`（改用 ctx.logger）。首页改为调用引擎。重复代码（publishXxx 四胞胎、备份五段、TFS/Git 日志 switch 两份）在搬运中按等价原则收敛。

**3b 全局调度器**：新建 `publishScheduler`，应用级启动 30s 轮询（不再依赖首页 keep-alive 存活）；定时执行从 `publishScheduleDb` 自建 ctx 调引擎；删除首页内的 `checkScheduledPublish / executeScheduledPublish` 与页面级定时器；任务执行日志独立留存（复用 `resultLog` 字段，成功也留存最后 2000 行）。首页顶部显示"⏱ 定时任务执行中 ×N"角标。同步退场第二批护栏：移除 `uiLocked` 中 `isScheduledRunning` 相关禁用（保留 `funModule loading` 部分），"同项目+同环境互斥"的排队/提示职责移交调度器。

**3c 定时任务页面**：在 `/publish` 分组下按兄弟路由惯例注册新页面——注意本仓库分组内子路由使用**根级绝对路径**（现有 `/home`、`/papersPublish` 即如此，实际 URL 不含 `/publish` 前缀），故新页面建议 `path: '/schedule'`、`name: 'schedule'`，菜单标题走 i18n `message.router.*`；现有 `scheduledPublishDialog` 的列表列/状态色/失败原因逻辑升级为页面。⚠️ 新建任务不能照搬对话框的上下文来源——现对话框依赖首页经 `openDialog(projectData)` 传入当前项目（无传入时拒绝保存），独立页面须自带选择能力：项目下拉查 projectDb、环境随所选项目探测可用环境（同 §2.3 的 `queryAvailableEnvironments` 模式）、发布类型按 settingsDb 的一键发布开关显隐，复用原表单校验规则。保留首页"定时发布"按钮作为快捷入口（弹窗或跳转）。`onDeactivated`/`onUnmounted` 的定时器生命周期问题随调度器上移一并消除。

### 4.4 并发策略

- 不同项目：并行（各持独立 ctx 与日志）；
- **同项目 + 同环境：互斥**，第二个任务给出显式提示（共享本地程序集输出目录，并行必出问题）；
- 手动发布与定时任务同规则。

### 4.5 等价重构纪律（对应决策 #14）

- 只做"机械搬运 + 参数化"，不改任何判断分支、错误文案、执行顺序；
- 每子步完成后完整手动回归：编译 / 获取程序集 / 手动发布 / 一键发布 / 定时发布 / 暂停-继续-停止 / 失败重试 / 发布前备份 / WpfClient 新旧版本两条链路；
- 每子步独立 git 提交（必要时短生命周期分支），可单独回退；本仓库版本控制为 git。
